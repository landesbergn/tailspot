Challenge invite links open the app

branch feat/challenges-universal-links · 2026-09-21 · Challenges v1 phase 3 · web + client · NOT yet verified end to end

https://tailspot.app/c/K7M4QD2X opens Tailspot straight into that invite's join sheet. Anywhere the app can't take it — desktop, Android, an iPhone without Tailspot — it goes to the App Store listing instead. There is no landing page: the link either opens the app or sells it.

Behaviours worth checking

SituationWhat happens
App installed, Challenges availableJoin sheet with the code prefilled, over the catch screen. Joining pushes the detail.
Link lands on a cold launch, before the config is knownThe code waits (.waitForConfig) while openInvite fetches the config, then opens. No error flash.
Link lands during onboardingThe code stays parked; the router delivers it when the catch screen first appears.
Build older than the server's minBuildAlert: "Update Tailspot to join this challenge", with an App Store button (the server's appStoreURL if it sent one).
Kill switch onTop toast: "Challenges aren't available right now." Nothing opens.
Another sheet already open (Hangar / Profile / Leaders)Replaced by Challenges. The user just tapped a link; the link wins.
Join sheet dismissed without joiningNothing re-presents — the hub takes the code off the model as soon as it has it.
Malformed link (/c/short, wrong host, extra path)Ignored by the parser. On the web it falls through to the 404 page.
Analyticschallenge_invite_opened fires once, from the join sheet, with the challenge id, via: universal_link and the joinability status. The router fires it only for the two blocked routes (status: update_required / unavailable), where nothing else would.

Manual checklist — Noah

None of this works until all three are done. The app half and the web half are each inert on their own, and Apple's cache sits between them.
  1. Enable Associated Domains on the App ID. Open the project in Xcode once → target Tailspot → Signing & Capabilities → + Capability → Associated Domains (or the developer portal → Identifiers → com.landesberg.Tailspot). Until this is on, any signed build — a bin/deploy to the phone, or Xcode Cloud — fails to sign with a profile/entitlement mismatch. The simulator doesn't check, which is why CI is green.
  2. Deploy the site: cd web && flyctl deploy --remote-only. Then check the origin directly: 
    curl -sI https://tailspot.app/.well-known/apple-app-site-association
# expect: 200, content-type: application/json, NO 301/302

curl -sI https://tailspot.app/c/K7M4QD2X
# expect: 302 → apps.apple.com/app/apple-store/id6773470079?pt=…&ct=Challenge%20Invite

curl -sI https://tailspot.app/c/nope
# expect: 404
  3. Let Apple's CDN catch up. https://app-site-association.cdn-apple.com/a/v1/tailspot.app shows what devices actually see; it can lag hours after a deploy. A device re-fetches the association on install and on app update, so the reliable test is delete-and-reinstall (⚠ that also destroys the local Hangar — use a test device or accept the loss knowingly).
  4. Then test the real thing: paste a /c/CODE link into Messages or Notes on the phone and tap it. It should open Tailspot, not Safari. Long-press the link: with the association live the menu offers "Open in Tailspot". If it opens Safari, the association isn't in place yet — check the CDN URL before changing any code.
