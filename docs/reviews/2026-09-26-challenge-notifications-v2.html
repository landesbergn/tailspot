Challenge notifications v2

branch feat/challenge-notifications-v2 · 2026-09-26 · client only · Challenges phase 3

Three gaps closed and one foundation laid. A 3d or 7d challenge had nothing at all between “it started” and the last hour. A challenge banner could land on top of the viewfinder, which is the one place the app has already decided never to interrupt. And tapping a challenge notification dropped you on the catch screen with no idea which challenge it meant. The fourth item is APNs registration: the client half of the remote overtaken push the backend is being built for in parallel.

Every moment, its timing rule and its copy

All five local moments come out of one pure function, ChallengeReminders.plan(...), recomputed on every sync (foreground, list refresh, create, join). Nothing is ever planned in the past, and nothing is planned at all unless the Challenges reminder toggle is on and iOS notifications are authorized.

Worked examples

  • 7d starting Monday 10:00 → daily on Tue, Wed, Thu, Fri, Sat and Sun, each at 17:00 (“Day 2 of 7” … “Day 7 of 7”). The end day is the following Monday, which is excluded — it already has ending_soon at 09:00 and finished at 10:00. (The brief's worked example read “Tue…Sat, not Sun the end day”, which assumes a Sunday end; 7 days from Monday 10:00 is Monday 10:00, so the stated rule — exclude the end day — gives Sunday a nudge 17 h before the finish. Flagged rather than special-cased, because the 3d example in the same brief pins the same rule.)
  • 3d starting Monday 10:00 → two dailies, Tue and Wed (“Day 2 of 3”, “Day 3 of 3”).
  • 3d starting Monday 00:30 → ends Thursday 00:30, so ending_soon falls at 23:30 on Wednesday, an otherwise-interior day. Wednesday's daily is dropped; only Tuesday's fires.
  • 24h starting 09:00 → midway 21:00 the same day. 20:00 → 08:00 next day. 22:00 → 10:00 next day. 14:00 → midpoint 02:00 is outside the window, so 09:00 next day. 10:00 → midpoint 22:00 shifts to 09:00 next day, which is the ending_soon instant — skipped.
  • 1h and 24h never get a daily; 1h, 3d and 7d never get a midway.

Where the placement comes from

A live placement exists only inside a fetched ChallengeDetail (list rows carry myResult for finished challenges only), so the model hands the scheduler whatever details[id].me it happens to have — from the hub, the Leaders strip, or a previous tap. That is deliberately allowed to be stale: the plan is recomputed on every sync, so a placement that moved is corrected the next time the app is open, and a day-old “You’re 2nd” beats a nudge with no standings in it at all. A placement is suppressed in a field of one — “You’re 1st” in a challenge you are alone in is a joke the app should not make.

One slot per day means a re-plan upserts that day's nudge rather than stacking a second one. Parsing now reads from the right, because a daily has two trailing components where every other moment has one; the id itself is a UUID, which can contain dashes but never a dot. identifiers(challengeId:startsAt:endsAt:) enumerates the per-day slots for cancellation, and cancel(challengeId:) additionally sweeps the pending list, so leaving a challenge clears its dailies even when the caller has no dates in hand.

Camera silence

The rule was already written down for the streak reminder: if you are pointing the camera at the sky, a banner telling you to go catch a plane is the app arguing with itself. That is just as true of “You’re 2nd in Weekend Flyoff”. willPresent now recognizes a challenge notification — anything carrying userInfo["challengeId"], or an identifier with the challenge prefix — and returns StreakReminders.foregroundPresentation(cameraFrontmost:): empty options (silent) on the viewfinder, [.banner, .sound] anywhere else. It calls the streak function itself rather than copying the rule, so the policy can only ever change in one place. Remote pushes obey it too. Streak behaviour is untouched.

Tap routing

A tap on any challenge notification — local reminder or remote push — opens that challenge's detail:

  1. didReceive (on StreakReminderCenter, which owns the process's one UNUserNotificationCenterDelegate) reads challengeId and kind out of userInfo, falling back to the identifier for a local one.
  2. It fires challenge_reminder_opened with challenge_id and moment (starts / midway / daily / ending_soon / finished / overtaken), then calls ChallengesModel.openChallenge(id:).
  3. The model parks a pendingDetailId — the same one-owner shape as pendingInviteCode, because a hub already on screen under Profile or Leaders would otherwise swallow it during its own sheet's teardown.
  4. ChallengeInviteRouter runs the existing ChallengeInvitePresentation sequence (dismiss whatever primary sheet is up, wait 450 ms for the dismissal, then present) onto PrimarySheet.challenges.
  5. The hub inside that sheet — source deep_link, the only source allowed to consume it — takes the id and pushes ChallengeDetailScreen.

The ChallengesModel is now built in TailspotApp.init and handed to the delegate there, not created inline: a cold-start tap is delivered before any view exists, and a delegate with no model would silently drop it.

APNs registration (client half)

New AppDelegate, wired with @UIApplicationDelegateAdaptor. SwiftUI has no equivalent of didRegisterForRemoteNotificationsWithDeviceToken, and the adaptor is how a SwiftUI App gets a UIKit delegate without giving up the SwiftUI lifecycle — body, scenePhase and .onOpenURL all keep working. Note that notification delivery and taps still go through UNUserNotificationCenterDelegate, a different protocol on a different object.

  • When it registers: at launch if notification authorization is already .authorized (tokens change on restore, on some OS updates, on reinstall — re-asking is the documented way to stay current and is cheap), and immediately after the challenge permission ask succeeds.
  • Environment: read at runtime from aps-environment in the bundle's embedded.mobileprovision. There is no API for this — the value lives in the code-signing entitlements, and the only runtime-readable copy is an XML plist embedded in that file's CMS blob, so the parser finds the <plist … </plist> window and decodes it. “development” maps to “sandbox”; “production” stays. This matters because a sandbox token sent to the production gateway is silently dropped — the classic “push never arrives”. Simulator or no profile → registration is skipped entirely.
  • Upload: PushTokenClient, POST /v1/devices/push-token, bearer auth from the same read-or-register path ChallengesClient uses, 15 s timeout, 204 expected. 
    { "token": "<lowercase hex>",
  "environment": "sandbox" | "production",
  "build": 120 }
    Idempotent against tailspot.push.lastUploaded in UserDefaults, so the every-launch re-register does not POST every launch — and a failed upload remembers nothing, so the next launch retries.
  • Failures: didFailToRegister logs and fires push_registration_failed.
  • Entitlement: aps-environment = development in Tailspot.entitlements. That is the right value to commit — Xcode and Xcode Cloud rewrite it to production when the app is archived, so the file never needs a per-ring edit. Nothing else in the pbxproj changed.

The remote payload (contract — the backend is built to this)

{ "aps": { "alert": { "title": "…", "body": "…" },
           "sound": "default",
           "thread-id": "<challengeId>" },
  "challengeId": "<id>",
  "kind": "overtaken" }

Nothing is rendered client-side — iOS draws the banner from aps. The tap comes back through the same delegate as a local reminder, which is why the local scheduler now writes the same two keys onto every request it adds.

Noah's manual steps, before any of the remote half works
  • Enable Push Notifications on the App ID (Xcode → Signing & Capabilities once, or the developer portal). Until then a signed device / Xcode Cloud build fails to sign — same failure shape as Associated Domains had.
  • Create and upload an APNs key for the backend.
  • The backend's overtaken sender and the /v1/devices/push-token route are being built in parallel to the contract above.

What this does not do. No new Settings toggle — the daily and midway nudges ride the existing Challenges reminders switch, which already governs the other three moments. No second permission prompt. No new rendering: a remote push is drawn by iOS, and the tap lands on a screen that already existed. And the backend half is untouched by this branch.
