Challenges v1 — client review fixes

branch fix/challenges-client-review · 2026-09-21 · client only · 13 findings + 7 review follow-ups, all with tests · full TailspotTests suite green

Follow-up to the phase-2 client merge (#277). Nothing here is new product surface: every change closes a hole the review found. The three that change what a user sees or what the data means are the compass-banner overlap, the share event, and the reminder permission.

The one you can look at: the DEBUG wrench was eating compass taps

The compass caution banner gets a region of 16 pt leading / 60 pt trailing, sized for the account button alone. In a DEBUG build the wrench sat beside that button, putting a 44 pt hit region at roughly x 295–327 on a 393 pt phone — on top of the banner's right end, where “tap to calibrate” lives. Every build Noah field-tests is a DEBUG build, so this is the build where a mis-calibrated compass is hardest to fix.

The fix keeps the Release layout and the banner width untouched: in DEBUG the wrench stacks below the account button, so the banner's row has one control on it.

The badge also moved out of ContentView into its own CautionBadge view. CompassWarningSnapshotTests was measuring a hand-copied duplicate of the badge markup — so its “fits in 317 pt” assertion could pass while the shipping badge didn't. It now renders the real view, and the 317 comes from TopStripLayout rather than being typed into the test.

What the layout tests actually pin, stated plainly: the strip's numbers (control diameter 44, top padding 8, trailing padding 12, banner insets 16/60) now live in TopStripLayout, which ContentView lays out with and TopStripLayoutSnapshotTests measures from. So the gate is on the constants ContentView reads — not on the frames SwiftUI ended up rendering, and not on the real buttons (which are private to ContentView and rebuilt in the harness). Put a second control back on the banner's row and the assertion goes red; the two images above are what show the actual result.

Notes for the reviewer

Two iOS patterns worth a second look

Generation counter (ChallengesModel.refreshList): each call bumps a counter, keeps its value, and on return checks whether a newer call has started. If so it writes nothing — not the list, not the error, not the spinner flag. This is the standard fix for “last response wins” when several callers can refresh the same state.

UIViewControllerRepresentable (ActivityShareSheet): SwiftUI's ShareLink reports nothing back, so the only thing it could measure was the tap. Wrapping UIKit's UIActivityViewController gives us completionWithItemsHandler, which is what turns challenge_invite_shared into an event that means what its name says. The mapping from UIKit's (activityType, completed) to our method is a pure static function, so it is tested without presenting anything.

What the permission ask does at runtime

It is awaited inside create/join, so the system prompt appears while the create sheet is still up and the push to the detail happens after the answer. That ordering is deliberate: the alert doesn't fight the share sheet. It is latched in UserDefaults (tailspot.challenges.remindersAsked) and the scheduler independently refuses to ask unless iOS says notDetermined, so there is no path to a second prompt.

What this does to challenge_invite_shared

Two things changed at once, and both matter for anyone querying it.

  • When it fires. It used to fire on the tap that opened the share sheet, so it counted openings — including every sheet dismissed without sharing. It now fires only on a completed share. Expect the number to drop; counts from before and after this build are different metrics and should not be compared.
  • What method means. The share-sheet path used to send the constant "share_sheet". It now sends the chosen activity type — com.apple.UIKit.activity.Message, com.apple.UIKit.activity.PostToFacebook, an app's own bundle id, and so on — with "share_sheet" kept only as the fallback when iOS reports a completed share without naming the activity. "copy_link" is unchanged.

So: filter on the property's presence, not on method = 'share_sheet'. A query written against the old constant will look like the feature died.

Not changed

No backend change, no schema change, no analytics event added or removed — the only data change is challenge_invite_shared's timing and method domain, described above. TailspotApp.swift URL handling and PrimarySheet.swift were left alone for the universal-link branch.

Review round two (the seven follow-ups)

  1. Regression caught in review. Stopping the poll for a status of .unknown also stopped it when the FIRST load had failed — no detail means no summary means unknown — so the error card could never heal itself. The wait table now keys off “has a detail” first: nothing loaded, keep retrying every 60 s; only a known-finished or known-cancelled challenge stops.
  2. Two syncs could double-report. The de-dup read the pending list across awaits, so overlapping syncs both saw it pre-add. Syncs are now serialized through a single in-flight task.
  3. The overlap gate measured the test's own constants. Now TopStripLayout, read by the view.
  4. The de-dup test recomputed the helper. Now asserted through Analytics._testSink — in AnalyticsFacadeTests, which is the one .serialized owner of that process-global.
  5. Dead constant and contradictory copy. serverMinLead deleted; the message quotes the picker floor.
  6. The method domain change is now called out here and in the CHANGELOG.
  7. Two comments made honest: the 60 s start lead also REMOVES an already-pending starts reminder inside that last minute (intended — a sync only runs because the app is open), and the invite-code strip set matches the backend's [\s-] in practice, not exactly: JavaScript's \s also matches U+FEFF, which whitespacesAndNewlines does not.
