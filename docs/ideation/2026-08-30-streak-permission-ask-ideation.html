Tailspot · streak reminders

The Three-Second No

Seven of eight testers refused notification permission. None of them read the card, and — it turns out — none of them actually spent the iOS prompt either.

Codebase Context

Tailspot schedules one local notification at 17:00 on days when a user has a live catch streak and hasn't caught anything yet. Because iOS shows the real permission dialog only once per install, the app gates that dialog behind its own card — streakAskOverlay in ContentView.swift — shown once ever, over the live viewfinder, after a catch reveal closes.

The card reads "Protect your streak?" above a line of body copy — "Turn on notifications to help keep your streak going." — with "Notify me" filled in cyan and "Not now" as a plain text button beside it. Its own source comment explains the intent: declining should stay "easy to hit and easy to read, without competing."

Across TestFlight builds 88 and 89 on 2026-08-29 and 30, eight testers saw it. Seven declined. Every decline landed between 1.46 and 5.54 seconds; the single acceptance took 17.82 seconds. Three people answered in under 2.5 seconds, which is less time than the card's two lines take to read. Streak size did not predict the answer: declines came at streaks of 1, 3, and 17, and the sole acceptance came from someone at a 1-day streak. The person with a 17-day streak — the most invested user in the sample — declined in 3.28 seconds.

Two further facts shape the ideas below. First, the card interrupts 12 to 60 seconds after a catch — while the user has gone back to the viewfinder hunting the next plane. Second, the streak ask and the App Store review prompt are both claimants on the same post-reveal moment, and they fire back to back: the 17-day-streak user got the review prompt 12.5 seconds after he dismissed the streak card (15.8 seconds after it appeared), and a second tester got it 26.9 seconds after his. The one person who accepted had his two asks separated by seventeen hours.

The finding that changes the options

requestAuthorization has exactly one call site in the app, inside requestPermission(), and only the "Notify me" branch reaches it. "Not now" fires telemetry and dismisses. All seven decliners are still .notDetermined at the OS level. iOS's genuinely scarce one-shot was never spent on any of them. The only thing standing between those users and a legitimate permission dialog is a UserDefaults boolean that Tailspot sets on itself, at the moment the card is presented — before anyone answers.

1

Settings is telling declined users they're covered

Axis 3 · permanence & recovery Confidence 95% Complexity Low
Description
Add a .notDetermined state to the REMINDERS section of Settings. Today that section branches only on .denied, so a user who tapped "Not now" — and is therefore .notDetermined — falls through both branches: the "Streak protection" toggle renders ON and undimmed, and the footer reads "Get notified if your streak is at risk." Nothing will ever fire. The only escape is toggling the switch off and back on, which triggers the permission request as a side effect nobody would guess at. The row should say reminders need one more step, and re-trigger requestPermission() on tap.
Basis
direct: SettingsScreen.swift — notifDenied is defined as notifStatus == .denied; the disabled-toggle branch, the "Open Settings" recovery row, and the alternate footer are all gated on it. The .onChange handler that calls requestPermission() only runs if the user flips a switch that already appears to be on. Confirmed independently by an adversarial verifier.
Rationale
The documented "only recovery path" is not merely hard to find — it is affirmatively misleading for exactly the population it exists to serve. Every other idea here is a judgment call about product design. This one is the app stating something untrue to seven real users, and it is worth fixing regardless of which direction the rest of this document goes.
Downsides
Fixes the honesty problem without moving the acceptance rate on its own — a user still has to open Settings and notice the row. Best shipped alongside idea 2.
2

Reclaim the seven — the latch is ours, not Apple's

Axis 3 · permanence & recovery Confidence 90% Complexity Low–Medium
Description
Separate the app's own latch from the operating system's. Replace the single permissionAskedKey boolean with a small ledger — attempts, last-shown date, and how long the answer took — and allow the card to return a bounded number of times, each gated on a genuinely different qualifying event rather than on the same trigger firing twice. Treat an answer that arrives faster than the card can be read as "not meaningfully shown" rather than as a decision. Then ship a one-time migration that clears the latch for any user recorded as declined whose OS status is still .notDetermined, which recovers all seven of the current cohort. Add seconds_to_answer to the ask telemetry so reflex and refusal stop being indistinguishable in the data.
Basis
direct: ContentView.swift:1603 sets permissionAskedKey at presentation, with the comment "Presenting latches the asked bit immediately, so it can never fire twice." StreakReminders.swift holds the app's only requestAuthorization call site, reachable from "Notify me," the Settings toggle, and a debug path — never from "Not now." shouldOfferAsk already takes alreadyAsked and authStatusIsNotDetermined as separate parameters, so the codebase encodes the distinction it then collapses. askResponseProperties carries no duration field.
Rationale
The feature inherited the irreversibility of the thing it was built to protect, for no technical reason. iOS's scarce resource was never at risk from a "Not now" tap. Recovering seven testers costs one migration and a second key, and it changes the value of everything downstream: better copy and better timing are worth far more when the app is allowed a second attempt than when it is chasing a single three-second reflex.
Downsides
Re-asking has a real annoyance ceiling; the bounded count and the "different qualifying event" rule are what keep this from becoming nagging, and both need a taste call. A dwell-time floor is a heuristic — someone who genuinely knows their answer and taps fast gets asked twice. The consumer-law analogy one frame offered for the dwell floor does not actually support it; the mechanism stands on the observed data alone.
3

Stop stacking two asks in twenty seconds

Axis 1 · the interrupting moment Confidence 80% Complexity Medium
Description
The streak ask and the App Store review prompt are both scarce, quota-limited requests living in the same post-reveal funnel, and answering the first currently unlocks the second immediately. Build one shared signal for "this is a reflective moment, not a reflex moment" — time since the last camera interaction, whether the app was freshly foregrounded, session depth — and gate both asks behind it, with a minimum quiet period between any two asks of any kind.
Basis
direct: PostHog, 2026-08-29/30: for the 17-day-streak tester, review_prompt_requested fired 12.5 seconds after he answered the streak card (15.8 seconds after it appeared); a second tester got the review prompt 26.9 seconds after his. The sole accepter's two asks were seventeen hours apart. The funnel's documented priority order places both in the same reveal-dismiss moment.
Rationale
Part of what reads as notification fatigue is the app asking for two different things inside half a minute, which primes exactly the dismissal reflex the telemetry captured. This also protects a second scarce resource nobody is currently watching: Apple silently caps review prompts, and the same mistimed moment is spending those too. One piece of shared infrastructure covers both, and any future ask plugs into it.
Downsides
The pattern appears clearly in two of eight cases, so it explains part of the decline rate, not all of it. Adding a moment-quality gate risks suppressing asks so effectively that they rarely fire at all — the gate needs a fallback so a user who never hits a "reflective moment" still gets asked eventually.
4

Ask at the loss, not at the win

Axis 1 · the interrupting moment Confidence 70% Complexity Medium
Description
Every ask currently fires at a moment of gain, because shouldOfferAsk requires a live streak — so by construction the card always arrives when nothing has been lost. Move it to the first app open after a streak has actually broken: "Your 6-day streak ended Tuesday. Want a heads-up next time?" The reminder itself still never nags a lapsed user; only the ask relocates. Three weaker variants of the same relocation are worth weighing against it: queue the card until the camera is no longer frontmost (reusing the cameraIsFrontmost() signal the delivery path already computes), stage it for a deliberate visit to the Hangar or Profile, or fire it only on the catch that just rescued an at-risk streak.
Basis
direct: StreakReminders.swift — "a lapsed user is NEVER nagged, because a reminder only exists while a streak is alive"; shouldOfferAsk requires currentStreak >= minimumStreak. Catch-to-ask gaps of 12, 18, 62 and 328 seconds put the card in the middle of active spotting. external: prospect theory — losses weigh roughly twice gains, and the streak break is the only moment the loss is real rather than hypothetical.
Rationale
This targets the fact the data is loudest about: streak size doesn't move the answer, and nobody in the sample was asked at a moment when the reminder's absence had cost them anything. It also gets the card off the viewfinder, where the user's momentum points at the sky and dismissal is the fastest way back to it. The self-contradiction is worth noting on its own — the app already refuses to interrupt a spotting session with a delivered reminder, then interrupts one with the card asking permission to send it.
Downsides
A broken streak may also be the moment a user is closest to churning, so the ask lands on a smaller and less enthusiastic population. It also delays the first ask substantially for users who never break a streak — which argues for pairing it with one of the softer relocations rather than replacing them.
5

Show the notification instead of describing it

Axis 4 · what the reminder promises Confidence 75% Complexity Low
Description
Two changes to what the card communicates. First, render the actual notification — StreakReminders.title and body, filled with this user's real streak number — as a lock-screen-style mock inside the card, instead of the softer paraphrase that has drifted away from it. Second, sell the restraint rather than the category: the scheduler already guarantees at most one message a day, only on days the streak is genuinely at risk, never after a lapse, and never while you are already pointing at the sky. None of those four guarantees is visible to the user. "One message. 5pm. Only when the streak is actually at risk. Never when you've already caught" is a materially different proposition from "turn on notifications."
Basis
direct: StreakReminders.swift — title and body are pure static functions already written in the app's dried voice, and the file header documents all four guardrails. The card's own copy is a separate, softer string. Nobody who declined has ever seen a Tailspot notification: streak_reminder_delivered has never fired for a real reminder. external: Breznitz, Cry Wolf: The Psychology of False Alarms (1984) — warning systems derive credibility from demonstrated restraint.
Rationale
This is the highest ratio in the feature of value already built to value communicated. The engineering did the restrained, careful work; the copy gives none of it away and asks instead for the one category people hold blanket policies about. It also merges two copy assets that must currently be kept in step by hand — every future edit to the notification retunes the card for free.
Downsides
Better copy cannot help a reader who answers in 1.46 seconds, so this is worth little on its own — it pays off only once ideas 2, 3 or 4 have bought the card an audience that actually reads it.
6

Make the decline mean what it says

Axis 2 · the card itself Confidence 70% Complexity Low
Description
"Not now" is false — it latches forever. There are three mutually exclusive resolutions and the choice is a taste call. Ship idea 2 and the label becomes true as written, which is the cheapest fix and the one I'd pick. Or relabel it honestly ("No thanks", with a line noting it can be turned on later in Settings). Or remove the decline button altogether, leaving one affordance — "Notify me" — and dismissal by tapping outside or swiping down, which fires its own event and never latches, making it structurally impossible to spend the ask on a reflex. A fourth framing is worth considering alongside these: replace the yes/no entirely with three time chips — 5pm, 7pm, 9pm — so that choosing an hour is the consent. A preference question has no reflex answer, and it would also fix a reminder hour that is currently hardcoded globally from one person's field test across a tester base spanning several time zones.
Basis
direct: the button label in ContentView.swift against permissionAskedKey's own doc comment, "the ask never repeats" — the two statements contradict each other and the user is acting on the button. The decline button's source comment states the design goal plainly: "declining stays easy to hit and easy to read." reminderHour = 17 is documented as "Fixed early-evening reminder hour (local). Not a setting in v1."
Rationale
The politeness affordance and the permanence mechanism are currently the same button, which is why a courteous design decision turned into seven permanent losses. Whichever resolution is chosen, the label and the behavior need to agree.
Downsides
Removing the decline button makes the card harder to escape, which cuts against the project's "gates flag, never block" principle if the dismissal gesture isn't obvious. The time-chip variant adds a persisted preference and a settings surface to maintain, and turns a one-tap ask into a small configuration task.
7

Surfaces that need no permission at all

Axis 5 · earning the nudge Confidence 65% Complexity High
Description
Three complementary ways to deliver the retention outcome without a dialog. A WidgetKit home or lock screen widget showing the flame, the day count, and today's state, cooling visibly as the day runs out — always present, no permission, no one-shot, and it works for the seven decliners today. An in-app toast on an at-risk evening after 17:00, reusing the StreakToastRelay and tapToastLine machinery already shipped for the notification-tap path. And a "sorry we missed you" slip: log locally what the 5pm nudge would have said, and surface it on the next app open — "5:12pm yesterday: your 6-day streak was one catch from ending. We didn't tell you." — with an inline enable control.
Basis
direct: StreakToastRelay and tapToastLine are shipped, working infrastructure. decision() is a pure function that already computes the at-risk state and stake, and currently drops both when the user is unauthorized — so the counterfactual costs a function call, not new logic. external: Darby, The Effectiveness of Feedback on Energy Consumption (Oxford ECI / DEFRA, 2006) — direct ambient feedback produces 5–15% behavior change against 0–10% for periodic reports.
Rationale
Every other idea optimizes a conversion rate on a permission most people appear unwilling to grant. These remove the dependency instead, and the slip has a second payoff: it is the only proposal that measures the counterfactual, telling you how often the reminder would have fired for the seven. That number is currently unknowable, and it is what determines whether this whole problem is worth more engineering.
Downsides
The widget is the most expensive item in this document: a new app-extension target plus an App Group entitlement for the SwiftData read, which is a manual Xcode step outside what Claude can do. It also waits to be looked at rather than arriving at 17:00. The toast and the slip are cheap by comparison and can ship first to test whether ambient nudging moves anything before committing to the extension.
